Design a browser extension UI from scratch. You are the independent product designer. You have not been given the existing UI, source code, screenshots, design system, component hierarchy, control labels, or navigation. Do not assume any. The user requested Claude Opus 5.5 at xhigh effort to design the UI blind, followed by a separate comparison against an existing implementation. Your assignment is design and a functional visual prototype, not backend implementation.

Product and audience:
A personal job-search companion for a technically literate early-career software engineer. It lives beside job websites in a Chromium browser side panel (Chrome/Dia on Mac), typically 360–450 pixels wide. Multiple remote agents also work with the same hosted job database. The owner wants to browse naturally and avoid passing files or data between agents. Choose the information architecture, visual direction, terminology, hierarchy and interactions yourself. Do not imitate a generic dashboard just to fit a template.

Required user outcomes (these are functional requirements, not prescribed screens or control layouts):
1. Browse LinkedIn, Jobright, Handshake or university Symplicity. Per site, choose automatic collection of observed listings, manual collection of explicitly selected jobs, or paused collection. Good recommendation boards may be automatic; noisy boards may be manual. Incomplete list-card records are valid leads. In manual mode, merely browsing other cards must not save them; revisiting already-saved jobs can enrich them.
2. Open a posting and expand its details. Add observed company, role, description, location, employment type, work mode, dates and URLs to the same stable job. Clearly distinguish an uncollected job, a saved partial lead, and saved details. Preserve useful prior text. Allow correcting fields; missing information is not a failure and should not trigger fake completion percentages. Mark description completeness only when justified.
3. Retain both the board posting URL and actual employer application destination (Workday/Greenhouse/Lever/Ashby/etc.). Recognized user-initiated Apply navigation can link the destination automatically; ambiguous destinations require explicitly choosing the matching saved job. Opening an application page does not mean submitting it.
4. Find saved jobs, inspect their details and collection status, and open the relevant URL. Expect hundreds of records, duplicate-looking job titles across companies/locations, and records shared with remote agents. Archive irrelevant opportunities reversibly with a reason; restore without losing history. Active application work must be resolved before archival. Incomplete leads should usually be enriched, not discarded.
5. Capture entered and prefilled application answers across pages/steps, including repeated work/education entries. Let the owner start, capture a section, pause/resume, review, correct or exclude an answer, preserve drafts and recognize unobserved sections. Finishing capture is distinct from confirming submission. Exclude passwords, verification codes and file contents. No accidental clicks on employer Submit.
6. Agents can queue blocked attempts for the owner (human review, login, missing information, CAPTCHA). Show the employer, role, blocker and resume instructions. The owner can take an item, open its application URL, select the saved page/step, and explicitly restore supported fields. Workday-style multi-step flows require step-specific restoration; login, file attachment and unsupported controls remain manual. Never automate CAPTCHA or employer submission. Preserve the original agent capture and later human edits. Leases prevent two workers doing the same attempt. Lost/expired ownership or uncertain submission must be visible and must not encourage duplicate submission.
7. Record the owner's intent to submit and, after an actual receipt or explicit owner confirmation, save one confirmed application and show readback. Collected leads, attempts, blocked items and confirmed applications are distinct. The applied tracker must not list skipped/blocked leads as applications.
8. Local saves can queue offline and retry. Distinguish saved locally, pending synchronization, synchronized, and a write requiring attention. Support recovery without losing drafts/settings. Version conflicts should not silently overwrite someone else's work. Keep rare maintenance separate from frequent browsing work.
9. One-time connection to a hosted API uses an owner-provided extension key. Never display the stored key or captured answers in diagnostics. Users can check connection/client compatibility, read what changed, export sanitized diagnostics, and follow a guided update/reload. An old verification check, offline state, incompatible client, and healthy connected state are different. Updates preserve identity/settings/drafts; no background updater or store listing is assumed. Keys and database implementation details should not dominate everyday UI.
10. Desktop keyboard accessibility, clear focus states, readable type, appropriate destructive-action treatment, and usable layout at 360px are required. No real network calls, secrets, personal data, application submission, or actual persistence to the user's database in the prototype. All examples must be synthetic.

Deliverables:
A. A cohesive design rationale explaining primary workflow, information architecture, visual direction, progressive disclosure, key decisions and tradeoffs. Include an explicit map of the major requirements to surfaces/states. Give concise microcopy for empty, partial, offline, blocked and uncertain-submission states. Identify any requirement the prototype only represents and any missing implementation work. Avoid claiming test results you did not run.
B. A self-contained, interactive HTML document (inline CSS/JS, no external assets/dependencies/network requests) that makes the chosen design reviewable in a real browser. Prioritize depth and coherence over a wall of static cards. Use realistic synthetic data. Make the main paths clickable: browsing/collection mode and selected-job save/detail enrichment; saved-job detail/archive; a blocked agent handoff with page selection and an explicit simulation-only completion flow; capture/draft review; and connection/recovery/diagnostics. Clearly label the artifact as a prototype and simulate all side effects locally. It should open in a desktop browser and present the actual narrow extension panel, with any scenario harness clearly outside the product. Include a way to examine at least a partial job, an offline queued save and an uncertain submission. You may choose how to organize these paths; do not mirror the order of this brief if another hierarchy is better.

Return the requested structured output. Explain intended behavior in the rationale, and deliver the complete HTML in prototype_html. No access to the existing implementation is available or needed.
